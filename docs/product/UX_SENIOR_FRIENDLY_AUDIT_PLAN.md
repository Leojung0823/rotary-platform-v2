# Rotary Platform V2：長輩友善 UI/UX 檢討與開發企劃書

## 1. 文件目的

這份文件是目前版本的 UX 總檢討，也是後續 UI/UX 開發的共同基準。目標不是把畫面做得更花，而是讓社員、社務幹部與平台管理員在第一次使用時就知道：

1. 我現在在哪一個扶輪社、哪一種工作模式。
2. 這一頁最重要的事情是什麼。
3. 按下去會發生什麼事，完成後下一步要做什麼。
4. 出錯時資料是否保留、要怎麼再試。

核心對象是年長社員。設計同時要適合手機、弱網路、放大文字、鍵盤操作，以及不熟悉系統術語的人。

## 3. 先講結論

目前平台的優點是：角色模式已經有清楚的方向、社員首頁已開始以「今天與我有關的事情」為中心、登入與資料隔離邊界不能被前端繞過、許多操作已有中文成功／錯誤訊息。

目前最需要處理的不是顏色，而是以下五件事：

| 優先 | 問題 | 使用者感受 | 先做什麼 |
|---|---|---|---|
| P0 | 角色脈絡解析失敗時退回舊殼 | 同一個帳號有兩套導覽，不知道哪個是真的 | 修正解析失敗原因；增加明確的重試與可觀測性；避免正常帳號落入舊殼 |
| P1 | 資料表在手機橫向溢出 | 文字被藏起來，要左右拖，長輩容易以為壞掉 | 名冊、出席、IOU、登入裝置、LINE OA 改成卡片或逐筆展開 |
| P1 | 主要控制項低於 48px | 按鈕難按、誤觸 | 社員流程統一至少 48×48px；管理頁也不要用 38px 代替主要操作 |
| P1 | 首頁與功能總覽層級混雜 | 重要通知、生日任務、祝福 IOU、功能地圖互相搶第一眼 | 首頁只放「現在要做的事」；開發地圖移出一般社員導覽 |
| P1 | 文字仍有工程術語與雙重入口 | 看到 OAuth、RBAC、Audit Log、作用社別，不知道要按哪裡 | 對社員用生活語言；技術細節放進「進階資訊」或平台管理員頁 |

## 4. 共通檢討與設計規則

### 4.1 長輩友善的最低標準

所有社員高頻流程都要符合：

- 主要按鈕與可點擊卡片的有效觸控區至少 48×48px。文字可以超過一行，但不能靠縮小文字來塞進去。
- 正文至少 16px；輔助文字不低於 14px。10–12px 只可用於不影響理解的品牌小字，不可用於主要狀態或操作。
- 手機 320px、375px、412px 都不能出現頁面級水平捲動。
- 文字放大 200% 仍能完成登入、看活動、報名、簽到、看名冊、寫祝福、看訊息與編輯個人資料。
- 一頁一個主要任務。次要操作收進「更多」或可理解的展開區，不與主要按鈕競爭。
- 所有錯誤都要說明「發生什麼事」與「現在可以做什麼」，且表單已輸入內容要保留。
- 成功後要告知下一步，例如「已送出，等待幹部發布」或「已完成，回到活動列表」。
- 不能用顏色當作唯一狀態；狀態一定要有文字。

### 4.2 角色與用語

| 技術或目前用語 | 社員／幹部建議用語 | 原則 |
|---|---|---|
| `社員模式` | 看社員功能 | 模式切換可保留，但說明要讓人知道用途 |
| `社務管理模式` | 管理這個社 | 只給幹部看，不必解釋後端權限 |
| `平台管理模式` | 平台管理 | 只給平台管理員看 |
| 作用扶輪社／作用社別 | 目前所在的社 | 不使用工程師的模型名稱 |
| Audit Log | 操作紀錄 | 需要時再顯示不可變更的歷史說明 |
| OAuth、CSRF、Replay、RBAC | 登入安全設定／角色權限 | 技術細節放「進階資訊」 |
| Follower／OA userId | 官方帳號好友／社員 | 幹部只在確實需要時看到代碼 |
| IOU | 祝福捐款承諾 | 第一次出現時解釋，之後可簡稱 IOU |
| 執行秘書 | 社務管理員（執行秘書） | 先講工作，再講正式角色名稱 |

### 4.3 導覽與資訊架構

社員第一層固定維持四項：`首頁`、`活動`、`社員`、`我的`。留言、生日、祝福 IOU、文件與出席由首頁任務或「社內互動／更多」進入，不應把低頻功能塞進第一層。

幹部第一層只放每天會用的工作：總覽、活動、出席、社員、訊息。生日徵集、文件、祝福 IOU、LINE OA、操作紀錄放在社務工具，但要用中文說明用途。

平台功能地圖不是社員功能。`/features` 與 `/features/[slug]` 目前會出現在一般登入者的導覽，應移至平台管理員或內部測試入口。

### 4.4 載入、錯誤與回復

目前只有 12 個頁面有頁面層級 `loading.tsx`；其餘頁面主要依靠共用 authenticated loading。共用骨架可以保住白畫面，但不應讓使用者看不到「目前正在載入哪一件事」。

優先為以下慢頁補上局部骨架：首頁內容、活動列表、社員名冊、訊息中心、出席、生日、祝福 IOU、文件、所有管理表格。資料失敗時保留頁面標題與目前社別，錯誤區塊直接提供「重新整理」或返回上一層。

每個危險操作都要在畫面上先說清楚影響：取消活動、停用 OA、解除 LINE Login、撤銷管理員、隱藏生日祝福、登錄收款、封存文件。瀏覽器的原生 confirm 不能取代中文說明與完成後回報。

## 5. 最高優先問題的修法

### P0-01：角色脈絡失敗造成兩套產品同時出現

**證據**：staging 首頁曾同時出現兩則新版角色脈絡失敗訊息，畫面卻顯示舊版「總覽／功能總覽／社員名冊／活動／留言板／會員中心／社團管理」導覽。這讓同一位社員在不同時刻看到不同資訊架構。

**建議修法**：

1. 先查明 `resolveExperienceContext` 失敗的實際原因，不以「保留舊版」當成正常成功路徑。
2. 在可授權的情況下，失敗頁只顯示保留登入狀態的明確錯誤、目前帳號與「重新整理」；不要混出第二套可操作導覽。
3. 如果真的需要 rollback，整個殼與首頁一起切換，不能只切導覽或只切內容。
4. 記錄不含姓名、Email、LINE subject 或帳號 ID 的失敗分類，方便定位資料／版本不一致。
5. 讓測試覆蓋：單社社員、多社社員、一般幹部、執行秘書、平台管理員、無有效社籍帳號。

**驗收**：上述角色在 staging 連續重新整理 10 次，導覽、首頁與目前社別始終同一套；遇到真正失敗時只看到一個可理解的錯誤狀態，且不洩漏其他社資料。

### P1-01：手機資料表改成「摘要卡片＋展開明細」

已實測的 320px 問題：

| 頁面 | 實測結果 | 建議 |
|---|---:|---|
| `/directory` | 頁面超出約 13px | 搜尋列固定一欄；社員改卡片，電話／Email 放次行 |
| `/me/security` | 頁面超出約 59px；兩張表 | 裝置與登入紀錄改成逐筆卡片；每筆只先顯示時間、方式、狀態 |
| `/attendance` | 頁面超出約 12px；兩張表 | 先顯示出席率與月份摘要，逐場紀錄用卡片 |
| `/clubs/:clubId/blessing-iou/reports` | 頁面超出約 435px；六欄年度表 | 月份與社員統計分成卡片／折疊列，手機不顯示六欄橫表 |
| `/clubs/:clubId/line-oa` | 頁面超出約 34px；兩張表 | follower 與推播紀錄逐筆卡片，完整 user ID 收進進階資訊 |

桌機可以保留表格，但手機必須有獨立呈現，不可只在外層加 `overflow-x: auto`。左右拖動只能作為管理員的最後備援，不能是社員的主要操作方式。

### P1-02：控制項尺寸與手機導覽

目前共用 CSS 的 `.button` 最小高度為 44px、`.input` 為 46px；實機還觀察到帳號選單 36px、帳號面板按鈕 38–40px、幹部次導覽 38px、手機導覽文字在 360px 以下降到 10px。

**建議**：

- 社員流程的按鈕、選單、輸入框統一至少 48px；管理頁的主要操作也採相同標準。
- 角色切換、社別切換、帳號選單的可點擊區至少 48px；圖示不能取代文字。
- 360px 以下不要再縮小主要導覽文字；改用較短但完整的詞，例如「社員」「我的」。
- 38px 的管理次導覽改成 48px，或改成可橫向捲動但每項可讀的下拉選單。
- 自訂 checkbox／radio 點擊外框至少 48px，保留目前勾選狀態與輔助文字。

## 8. 驗收與測試規格

### 8.1 每一個 UI PR 的最低驗收

- 320px、375px、412px：無頁面級水平溢出。
- 200% 文字放大：主要按鈕、表單、錯誤、返回路徑仍可見。
- 鍵盤：Tab 順序合理、焦點不被固定底部導覽遮住、表單錯誤會移到第一個錯誤欄位。
- 觸控：主要操作至少 48×48px；checkbox／radio 的文字與外框都可點。
- 載入：弱網路時先看到與任務相符的骨架，不出現長時間白畫面。
- 錯誤：保留已輸入內容，說明原因與下一步，不把資料庫錯誤誤顯示成空資料。
- 權限：一般社員直接輸入管理頁 URL 仍由後端擋下；隱藏連結不能被當成授權。
- 隔離：切換社別後，標題、列表、操作與錯誤訊息全部屬於同一個社。
- 隱私：不在社員頁顯示作者、完整生日、登入識別碼、LINE subject、內部角色代碼或不必要的金額。

### 8.2 自動化檢查建議

新增或補強：

- `e2e/tests/member-navigation.e2e.mjs`：四個第一層導覽與返回路徑。
- `e2e/tests/member-mobile-ux.e2e.mjs`：320px、375px、412px 溢出與觸控尺寸。
- `e2e/tests/management-mobile-ux.e2e.mjs`：管理模式、社別切換、不可逆操作提示。
- `src/lib/experience-context*.test.ts`：解析成功、失敗、降級與錯誤分類。
- DOM assertion：`document.documentElement.scrollWidth <= document.documentElement.clientWidth`。
- DOM assertion：社員高頻流程可互動元素的寬高至少 48px。

測試不得使用 `force: true` 來掩蓋底部導覽或遮罩問題；要修正真正的重疊與焦點順序。

### 8.3 發布門檻

在五人測試前，不宣稱「長輩友善已完成」。至少要有：

- P0-01 通過。
- IOU 年度報表、登入安全、社員名冊、出席的手機溢出為 0。
- 主要社員操作的 48px 觸控與 200% 放大驗收通過。
- 真實 iOS Safari 與 Android Chrome 各至少一次。
- 五位使用者完成測試任務，重大卡點已修正或有明確豁免理由。

## 9. 不可違反的邊界

- 不因 UX 方便而移除 RPC、RLS、後端角色判斷或社別隔離。
- 不把登入狀態、權限、社員名單、作者或財務紀錄放進公開快取。
- 不把技術錯誤字串直接顯示給社員，也不把錯誤當成空資料。
- 不在本企劃的 UI PR 中新增資料庫結構；若流程真的需要資料模型，另開產品與安全評估。
- 不把平台管理、社務管理、社員功能混在同一個導覽。
- 不用「看起來像完成」的假資料或假按鈕替代實際流程。

## 11. 完成定義

這份企劃書的「完成」只代表 50 個 page route 已完成盤點並有對應建議；不代表產品已完成上述 UI 改造。

產品 UI/UX 全部完成的條件是：P0/P1 工作已通過對應測試、五人長輩測試完成、真實手機驗收完成、角色與資料隔離沒有退步，並且每一項未完成事項都有明確負責 PR 或豁免紀錄。

- 首頁與錯誤狀態：社員首頁先顯示標題與主要內容骨架，再載入 LINE OA 與次要入口；登入後錯誤改用友善的重試畫面，不直接把技術錯誤字串顯示給社員。
- 導覽與資訊架構：一般社員不再看到平台功能中心連結；功能頁仍由後端平台權限保護，舊的返回路徑改回工作台。
