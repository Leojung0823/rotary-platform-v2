## 為什麼先寫規格

目前待辦只寫了「應收、部分收款、代墊、核銷」，但沒有定義每一種金額的生命週期。這是財務資料，不能直接把舊專案的單一 `admin` 權限與資料表 CRUD 搬進來。本文件已把可實作範圍與六項 V1 規則定案，並依「資料模型與 RPC → 管理頁 → 社員查詢 → 匯出」切片實作。

## 建議的 V1 範圍

- 依扶輪年度建立社費或活動費應收項目。
- 應收項目綁定本社社員，可分次登錄收款。
- 收款金額不可超過剩餘應收；部分收款自動顯示剩餘金額。
- 錯帳不刪除，使用反向調整保留完整軌跡。
- 代墊先記為「社員替本社支出的待核銷款」，核銷後才結案；不能與社員捐款或社費混成同一種餘額。
- 管理者可查詢本社扶輪年度彙總；一般社員只看自己的應收與收款狀態。
- 不做線上刷卡、銀行自動對帳、發票、稅務或會計總帳。

## 建議資料概念

第一版應至少分開三種不可混用的軌跡：

1. `receivables`：本社向社員收取的社費／活動費。
2. `receipts`：實際收到的款項，可一筆對多筆應收，也可多筆對一筆應收。
3. `advances`：社員或幹部代本社支付的款項，另有核銷與反向調整。

所有資料都必須帶 `club_id`，扶輪年度用日期計算或綁定既有年度，不使用跨社共用快取。

## 權限建議

- 新增一個明確的 `finance.manage` domain permission，由社長、秘書、財務及經授權的執行秘書使用。
- 平台管理員不因平台身份自動取得某社財務資料；若需要平台支援，另設明確的 platform audit 流程。
- 所有新增、收款、核銷、反向調整都走固定 `search_path` 的 SECURITY DEFINER RPC。
- 瀏覽器不可直接讀寫財務表；管理模式只是入口，不是授權來源。
- 每次變更寫入 append-only audit，不能把原始收款改成另一筆數字。

## 已採用的 V1 預設（2026-09-14）

以下內容是已核准、可直接實作的業務規則：

1. **應收金額**：每位社員每個扶輪年度建立一筆應收，可先用年度預設金額產生，再允許幹部對個別社員調整；調整要留下原因與稽核紀錄。
2. **收款方式**：V1 先記錄現金、轉帳、支票與其他，暫不做線上付款、銀行串接或自動對帳。
3. **權限分工**：具 `finance.manage` 的財務可登錄應收與收款；社長／秘書或被授權的財務主管可核准核銷。平台管理員不因平台身份取得社內財務權限。
4. **部分與超額**：允許部分收款與部分核銷；超過剩餘金額的請求直接拒絕。退回後可以重新送件，已入帳資料只能用反向調整，不直接編輯或刪除。
5. **舊帳匯入**：V1 不做批次匯入；若需要期初餘額，由幹部逐筆建立並填寫來源與說明，之後再另立匯入規格。
6. **社員可見內容**：社員可查看自己目前應收、已收、剩餘金額與收款明細；看不到其他社員的財務資料。

本領域依序拆成「資料模型與 RPC → 管理頁 → 社員查詢 → 匯出」四個可獨立審查的工作。若未來要改規則，先修改本節與驗收條件，再新增 migration，不回寫已部署的資料庫結構。

## 驗收條件

- A 社財務人員不能讀或改 B 社資料。
- 一般社員、外社社員、停權帳號與平台純管理員不能取得未授權的社內財務明細。
- 部分收款、反向調整、代墊與核銷的金額守恆可由資料庫驗證。
- 原始紀錄不可刪除或覆蓋，稽核可追到操作者、時間、原因與前後差額。
- 重複送出不會產生兩筆收款；金額不會因重試增加兩次。
- 報表與匯出使用 `no-store`，不包含 token、Auth UUID 或不必要的個資。
- 通過本機 DB verification、跨社負向測試、管理／社員模式測試後，才進 staging 真人驗收。
